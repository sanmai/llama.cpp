# Walk Backwards towards Simplicity

Proposed strip order (each = one variable, requantize + KLD on 27B, native path):

- Stage 0: N4_K as-is (pow2 s_global + .scale epilogue + LS bias) — n4k-pow2.gguf, already built
- Stage 1: drop LS bias (keep pow2 + .scale)
- Stage 2: drop .scale epilogue → single-level nvfp4 + MSE search = n4_0+search (recovers full speed; the one perf cliff)
- Stage 3: drop MSE search → bare n4_0
- Reference columns: q4_0 (0.0485), q3_k, stock nvfp4

All KLD: native FP4 path, `wiki.test.raw --chunks 200 -c 512 -b 4096 -ub 2048 -fa on -ngl 999`,
base `kld-base/qwen3.6-27b-f16-kld-base.dat`, via `./scripts/nvfp4-weight-kld.sh`.
Measurement order is Stage 0 -> Stage 2 first (the decisive "does .scale earn its keep" question);
Stage 1 only if Stage 2 falls back toward q3_k.

## Results so far

| stage / arm                   | Mean KLD | Same-top-p | size | .scale | speed         |
|-------------------------------|----------|------------|------|--------|---------------|
| Stage 0  N4_K (pow2+scale+LS)  | 0.069253 | 89.539%    | 16G  | yes    | epilogue tax  |
| Stage 1  pow2 + .scale (no LS) | -        | -          | -    | yes    | epilogue tax  |
| Stage 2  n4_0+search (= F4_0)  | 0.078843 | 88.841%    | 16G  | no     | full native   |
| Stage 3  bare n4_0             | 0.089396 | 88.051%    | 16G  | no     | full native   |
| ref  q4_0                      | 0.048516 | 91.737%    | 15G  | -      | W4A8 (no FP4) |
| ref  q3_k                      | 0.082717 | 88.792%    | 13G  | -      | -             |

Key reading: N4_K (0.0693) beats the size-class competitor q3_k (0.0827) by -16%; q4_0 leads on
quality (0.0485) but runs W4A8 — no FP4 prefill win. The decisive Stage 0 vs Stage 2 result:
**the .scale machinery buys -13.8% KLD (0.0789 -> 0.0693) at a ~8% prefill / ~4.6% decode tax and
~120 producer lines.** This flips the 7B story (where n4_0+search beat the tricks) — at 27B the
per-tensor global scale earns its keep. But n4_0+search (0.0789) still beats q3_k (0.0827) on its
own, at full native speed: the simple format already clears the size-class bar.

# Stage 0 - N4_K (pow2 s_global + .scale epilogue + LS bias)

`qwen3.6-27b-n4k-pow2.gguf`, build 7d072385a. 503 NVFP4 matmul weights + 503 F32 `.scale`
(+ `.input_scale`=1.0), token_embd/eh_proj Q8_0, output Q6_K.

- Mean KLD 0.069253, Same-top-p 89.539%, 16 GiB.
- Beats q3_k (0.0827) by -16%; trails q4_0 (0.0485).
- Carries the two-level scaling cost: a separate `ggml_mul(res, .scale)` per matmul = ~8% prefill,
  ~4.6% decode vs scale-less nvfp4 (see `bench-n4k-pow2-vs-q4_0.md`).

# Stage 2 - n4_0+search (no .scale, full native speed)

Producer stripped to NVFP4 ftype plumbing only (the entire `.scale` layer removed: pow2 prescale,
LS bias, `.scale`/`.input_scale` writes); MSE +-2 scale search retained in `ggml-quants.c`.
`qwen3.6-27b-n4_0-search.gguf`, overrides matched to Stage 0 (token_embd/eh_proj Q8_0, output Q6_K)
so the only difference is the `.scale` layer. 4.79 BPW (leaner than N4_K's 16G — no .scale tensors).

- Mean KLD **0.078843**, Same-top-p 88.841%. Smoke: SOUND.
- vs Stage 0 N4_K: **+13.8%** KLD (0.0693 -> 0.0789) — the .scale layer's quality contribution.
- vs q3_k (0.0827): **-4.7%**, and Same-top-p essentially tied (88.84 vs 88.79). So the simplest
  arm still beats the size-class competitor, at full native FP4 speed.
- Forward-compatible by construction: no `.scale` in the file, but a future `.scale`-aware loader
  reads it fine (TENSOR_NOT_REQUIRED + `if (w_s)` guard in `build_lora_mm`) — the .scale layer can
  return later as an opt-in higher-quality variant on the same format without a re-spin.

# Stage 3 - bare n4_0 (no search)

`qwen3.6-27b-n4_0.gguf`. ggml-quants.c reverted to master (`quantize_nvfp4` -> `quantize_row_nvfp4_ref`,
no MSE +-2 scale search); stripped producer unchanged. Same overrides, same 4.79 BPW. Smoke: SOUND.

- Mean KLD **0.089396**, Same-top-p 88.051%.
- The MSE search buys **-11.8%** (0.0894 -> 0.0789) at **zero inference cost** (quantize-time scale
  choice only — identical format, identical native kernel, identical speed).
- Decisive: bare n4_0 (0.0894) *loses* to q3_k (0.0827); n4_0+search (0.0789) *beats* it. The search
  is the difference between clearing the size-class bar and not. Definite keep.

# Verdict - F4_0 = n4_0 + MSE search

Locked. F4_0 is single-level NVFP4 (per-16 UE4M3 block scales, standard codec) + the quantize-time
MSE +-2 scale search, **no `.scale` epilogue, no per-tensor global scale, no MoE plumbing**.

- KLD 0.0789 on 27B: beats q3_k (0.0827), behind q4_0 (0.0485, but W4A8 = no FP4 prefill win).
- Full native FP4 OMMA prefill speed (no `ggml_mul` epilogue) — F4_0's whole reason to exist.
- Producer = NVFP4 ftype plumbing only (2 lines vs master); search lives in `ggml-quants.c`.
- Forward-compatible: emits no `.scale`, and a future `.scale`-aware loader reads it fine
  (`TENSOR_NOT_REQUIRED` + `if (w_s)` guard) — the N4_K `.scale` layer can return later as an
  opt-in higher-quality variant on the same GGUF format, no re-spin needed.
- The `.scale` layer (N4_K, Stage 0) remains a documented option: -13.8% KLD (0.0789 -> 0.0693)
  for ~8% prefill / ~4.6% decode + ~120 producer lines. Spends the speed advantage F4_0 exists for,
  so it stays out of the deployable default.

# Real-world perf (llama-server, 27B, RTX 5090)

`llama-server --jinja -fa on -np 1 -ctk q8_0 -ctv q8_0 -b 8192 -ub 4096 --temp 0 --top-k 1 --seed 1`,
same 2322-token prompt. (`n4_0.gguf` = bare, but perf is identical to `n4_0-search.gguf` — search is
quantize-time only.)

| metric             | q4_0                  | n4_0 (F4_0 format)    | delta        |
|--------------------|-----------------------|-----------------------|--------------|
| prefill (2322 tok) | 3487.82 t/s           | 4788.37 t/s           | **+37.3%**   |
| decode             | 74.15 t/s (13.49 ms)  | 74.06 t/s (13.50 ms)  | -0.1% (flat) |
| power (spot)       | 459-489 W             | 488-499 W             | ~+10-30 W    |

Confirms the thesis on a real prompt: +37.3% prefill (matches/beats the inherited +34.9%), zero
decode-speed tax. Power nuance: F4_0 draws ~10-30 W more; prefill is short enough that prefill
energy/prompt drops, but decode runs same-t/s at ~5% more watts (E2M1 LUT + UE4M3 unpack = extra ALU
that doesn't slow the bandwidth-bound GEMV). So energy/prompt favors F4_0 on prefill-heavy workloads,
~neutral on decode-heavy. Coarse spot readings - directional, not a measured joule count.

# Measured per-phase energy (`scripts/power-probe.sh`, 27B, RTX 5090)

Phase-separated J/tok = steady-state active power / throughput (no integration; 120 s idle settle
for a clean baseline). Prefill is REAL text (benchmark.bin, ~74.5K tokens) via llama-completion;
decode is llama-bench tg256, -r 20. `-b 8192 -ub 4096`, q8_0 KV.

| phase   | q4_0                  | n4_0 (F4_0)           | speed   | energy/tok       |
|---------|-----------------------|-----------------------|---------|------------------|
| prefill | 2882.7 t/s @ 560.8 W  | 3645.8 t/s @ 556.7 W  | +26.5%  | 0.195 -> 0.153 J (**-21%**) |
| decode  | 82.6 t/s @ 519.8 W    | 82.4 t/s @ 542.4 W    | -0.2%   | 6.297 -> 6.585 J (**+4.6%**) |

- **Prefill: +26.5% faster at equal power -> -21% energy/token.** Big, stable win. (+26.5% vs the
  server's +37% = O(n^2) attention dilution on a 74.5K-token prompt; short prompts trend to +37%.)
- **Decode: same t/s, +22 W -> +4.6% energy/token** (noisy run-to-run, +4.6 to +7.8%, but always
  positive - the E2M1-LUT/UE4M3-unpack ALU shows as heat without slowing the bandwidth-bound GEMV).
- Net: energy/prompt favors F4_0 on prefill-heavy workloads, ~neutral-to-slightly-worse on
  decode-heavy. Now measured, not a spot-read guess.
